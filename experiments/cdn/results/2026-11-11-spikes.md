## #248: which pyrail fields can the CDN data fill?

| pyrail field(s) | Source in the CDN data | Status |
|---|---|---|
| Station: `@id`, `id`, `latitude`, `longitude` | `stops` / `stations` tables: IRI `http://irail.be/stations/NMBS/008814001`, coordinates. `id` is `BE.NMBS.` + the number. | available |
| Station: `name` (per language), `standard_name` | `stopEnrichment` (`nameNl/Fr/De/En`) and `stations` (`name`, `alternativeFr/Nl/De/En`). Which column equals the API's `standardname` is not verified. | available, verify |
| Vehicle: `name`, `short_name`, `number`, `type`, `@id` | `tripEnrichment.vehicleIri` (`http://irail.be/vehicle/IC2130`); the pieces are derivable (`IC 2130`, `IC`, `2130`). The split rule for unusual types is not verified. | derivable, verify |
| Vehicle: `longitude`, `latitude` | The recorded API examples return `"0"` for both. Nothing to fill. | drop or `None` |
| Delay, `canceled`, skipped stops | GTFS Realtime trip updates. Needs the trip-id fix below. | available |
| Platform `name` | Realtime stop ids carry it (`8896800_1`; 96% of stop updates). The connection pages have **no platform column**, although 91% of `stop_times` rows in the official static GTFS name one. So a platform is known only for trips whose realtime update names one: **10%** of the trips running that service day (255 of 2626 in a later snapshot: distinct trips whose update resolved to a trip running that service day and names a platform, counted by `analyze_realtime.py`). | mostly missing |
| Platform `normal` | Needs the scheduled platform next to the actual one. | missing |
| `occupancy` | `irail.json`: occupancy "unavailable". | missing |
| `left`, `arrived` | No stop-status feed ("stopStatus" unavailable). Could be approximated from the clock (departure plus delay is past); that is a guess, not status. | missing, approximable |
| `is_extra`, `is_extra_stop` | The snapshot had no added trips (4 canceled, 356 scheduled). The planner ignores trips not in the timetable. | missing |
| `departureConnection` | New IRIs (`https://irail.be/id/nmbs-sncb/runs/.../connections/7`) replace `http://irail.be/connections/8892338/20250106/IC3033`; the old form can be rebuilt from stop number, date and vehicle, but it is not unique (the CDN notes 739 duplicate train-days). | derivable, differs |
| Direction `name` | `headsigns` table: `translationNl/De/En`, French is the source. | available |
| `vias`, `duration`, `stops` | From the planner / the connection list. | derivable |
| Connection `remarks`, `alerts` | Alerts "unavailable". | missing |
| Composition, disturbances | Not in the data (see #249). | missing |

### Realtime feed versus timetable (matters for #253)

- The first snapshot had 360 trip updates for 2623 trips running that day (an update-to-trip ratio of **14%**); a later one 266 for 2626 (**10%**). All carry delays; it looks like a feed of deviations, not of every trip. This ratio counts updates, not platforms: see the platform row above.
- 130 of 360 (**36%**) do not match a trip in `trips.arrow` by the documented template
  (`https://irail.be/id/nmbs-sncb/trips/{trip_id}`); in the later snapshot 94 of 266 (**35%**). All of them match
  once the **last field of the trip id** is ignored (feed: `...:20271211`, table: other dates), and **each
  resolves to exactly one trip that runs on that update's own `start_date`** (`analyze_realtime.py` filters the
  candidates by the update's `start_date`; in both snapshots every update had the same one, the snapshot's day).
  So: match by exact trip id first, then by (trip id without its last field, trips running on `start_date`). A
  planner that only uses the template silently loses over a third of the delays.
- Likely cause (not confirmed): the feed and the CDN timetable come from different static GTFS versions. The
  official static feed fetched the same day has `feed_info` version `2026-11-10`, valid to `20271211`, while
  `irail.json` says the CDN was built from version `2026-11-11`, valid to `20270930`.
- Only the scheduled platform is missing from the connection pages; the converter reduced platforms to
  `platforms.arrow` and `stop_time_overrides.txt` is not published (`irail.json` notes).

## #261: is plain Python fast enough for a connection scan?

`planner_spike.py`: earliest-arrival Connection Scan, standard library only, over real pages. Not a correct
router (no walking, transfers table, realtime or in-seat transfers).

| Query (08:00 Brussels, 12 Nov) | Earliest arrival | Live iRail API |
|---|---|---|
| Brussels-South to Antwerpen-Centraal | 08:07Z | 08:07Z |
| Gent-Sint-Pieters to Liege-Guillemins | 08:59Z | 08:59Z |
| Oostende to Arlon (transfers) | 11:22Z | 11:22Z |

- Decoding the 5 pages of a 24-hour window takes **66 ms** and brings peak memory to **68 MB** (39 MB at start); a
  "48-hour" window of 7 pages takes 78 ms and 99 MB. These first-run counts (65,539 and 92,612 connections) are
  **whole-page** counts, and that 7-page sample did not cover a full 48 hours, so the 48-hour figures are not
  comparable. Complete-window measurements (24 h: 5 pages, 48,440 connections; 48 h: 9 pages, 92,103
  connections, scanning only the departures inside the window) are in `2026-11-11-gaps.md`.
- One search takes **1 to 2 ms** because the scan stops at the first arrival; six searches (a stand-in for six
  alternatives) take 2 to 14 ms. The worst case, a target that cannot be reached so the whole day is scanned,
  takes **13 to 28 ms**.
- So the cost is dominated by loading pages, not by the scan. Pure Python is fast enough for earliest arrival on
  this hardware. Still to do: a real profile search with alternatives and arrive-by, walking and transfers, and a
  run on Raspberry Pi-class hardware, which will be several times slower.
