# Follow-up: CDN measurement gaps (#247, #261)

Raw measurements: [planner JSON](2026-11-11-planner-profile.json) and [reader / realtime comparison](2026-11-11-followup.md).

Measured 2026-11-11T18:44:44.756762+00:00 on x86_64, Python 3.12.13, Linux-7.2.15-300.fc45.x86_64-x86_64-with-glibc2.44. Release `nmbs-sncb-20261111-5c05082d`, sampled from 2026-11-12. No Pi-class hardware was available.

## Method

Each window and storage variant runs in a fresh subprocess. Queries start at 08:00 Europe/Brussels; arrive-by deadlines are 24 or 48 hours later. The downloaded sample spans both full windows. Only connections departing inside each window are scanned, although Arrow decoding necessarily reads whole overlapping pages. The old report used whole-page row counts and had only eight sampled pages; its nominal 48-hour window was not guaranteed to have complete coverage.

Sorting, decode and profile times are single samples. Individual scans use the best and median of five repetitions; the table below uses medians. Process peak RSS includes loading, sorting, conversion and all searches in that worker. It is not retained data size. CPU scheduling and frequency affect these numbers; do not infer scaling from small differences between windows.

The profile scans once per distinct boardable departure from the source, then removes dominated departure/arrival pairs. It computes actual alternatives in the simplified model, rather than using six arbitrarily spaced queries as a proxy. This is a deliberately naive baseline, not a profile-CSA implementation. Arrive-by uses a reverse scan; synthetic tests check transfer time, staying on the same trip, pickup/dropoff restrictions and unreachable targets. Real-data runs check early-stop versus full-scan equality and that arrive-by departures can meet their deadlines.

## Recommendation

- Start #258 with Python tuples and a sorted connection list. Early stopping reduces work for reachable targets; an unreachable target still needs a full scan. Sorting is measured separately; it is a correctness prerequisite if input order is not guaranteed, not an optional faster scan over unsorted data.
- NumPy 2.5.4 int64 row storage did not improve this Python loop. The optional probe includes conversion and produces the same arrival values as tuple storage. This does not rule out a compiled algorithm or vectorized preprocessing; sequential reachability updates remain Python work in this probe.
- Individual scans support a pure Python starting point on this machine. A full departure profile costs much more than one scan: use a profile algorithm, a bounded departure interval, or caching rather than treating six searches as a full profile. Benchmark that implementation before choosing dependencies.
- Keep the in-repo Arrow reader with no runtime Arrow dependency. The new reader run matches PyArrow and arro3 on all 16 files; nanoarrow still rejects this file layout. Use gtfs-realtime-bindings/protobuf for realtime parsing when that backend is implemented. They remain experiment dependencies here; the optional-versus-required packaging decision belongs with that backend.

## Remaining limits and issue status

- **#247:** the library recommendation and reproducible resource measurements exist. Raspberry Pi / Home Assistant-class measurements are unavailable; the original issue says "if available". Record this as deferred hardware validation rather than claiming an ARM result. Re-run these commands when hardware is available.
- **#261:** earliest-arrival, arrive-by, departure-profile and unreachable-target costs are now measured, including sorting, early stopping and a NumPy storage probe. The spike supports a starting design for #258; it does not establish production-router performance.
- Walking/footpaths, the transfers table, realtime and in-seat transfers remain outside this prototype. Validate and measure them in #258. Per-stop minimum transfer times and remaining on the same trip are included. The profile optimizes departure and arrival time only, not number of transfers or walking.
- These are cached local-file measurements. Network download, cold filesystem-cache behavior and constrained-device latency are not established. No issue is automatically closed by merging this PR into CDN-rebase.

## Reproduce

```bash
python experiments/cdn/fetch_data.py data --date 2026-11-12 --pages 12
uv run --group experiments python experiments/cdn/compare_all.py data --write readers.md
uv run --with numpy==2.5.4 python experiments/cdn/planner_benchmark.py data --numpy --write planner.json
uv run python -m unittest discover -s experiments/cdn -p 'test_*.py'
```

Choose a date inside current CDN coverage. Insufficient page coverage or missing/mismatched sample metadata is rejected rather than silently labeling an incomplete window. Full NumPy scans are measured in separate workers; arrive-by and profiles use tuples only.
